## #51 — Finalize cancel-before-create: non-locking re-read leaves a narrow TOCTOU window (spec 06)

**Premise verdict: `AS_DESCRIBED` · severity high · confidence high · reachable with the shipped adapter: **Yes — the only one****

### What the code does today

END-TO-END, WHAT THE CODE DOES TODAY ON THE CANCEL-BEFORE-CREATE PATH

Entry and inputs. `FinalizeBookingCommandHandler.Handle` (FinalizeBookingCommandHandler.cs:87) receives a `FinalizeBookingCommand(TenantId, OperationId)`, dispatched by `AdvanceBookingOperationCommandHandler`'s drive loop (AdvanceBookingOperationCommandHandler.cs:74-92) whenever `op.Status == Finalizing` and `OperationType == Create` (StepCommandFor, 155-160), or from `Held` after RequestPayment routes forward. The driver holds NO lock or lease on the operation — its inbox admit is explicitly "best-effort ... does NOT gate execution" (57-69) — and it re-loops immediately on `StepOutcome.Continue` (90-91), up to 20 iterations. Three hosted services publish into that same driver in parallel: `OutboxPublisherHostedService`, `ScheduledJobPollerHostedService` and `StepSweeperHostedService` (MessagingServiceCollectionExtensions.cs:37/41/45), all three routed to the same `AdvanceBookingOperationCommand` factory (ApplicationServiceCollectionExtensions.cs:85-96, message types `booking.command.requested.v1`, `booking.step.continue.v1`, `booking.reconcile.requested.v1`). The sweeper republishes a continuation for every stale non-terminal `workflow_step` (StepSweeperHostedService.cs:60-95). Two concurrent drivers on one operation is therefore an ordinary configuration, and per spec 06 §7 (line 304) the ONLY defence is the version-guarded conditional UPDATE.

The reads the branch decides on. At line 89 the handler loads `op` (BookingOperationRepository.GetAsync, 32-35: `.AsNoTracking()`, no lock). Lines 94-95 bail with `Continue` unless the status is `Held` or `Finalizing`. Line 101 derives the stable provider idempotency key from `(operationId, "finalize", op.IntentRevision)`; lines 104-106 load the intent revision for `requestHash` and `canonicalPayload`. Line 114 takes the pre-transaction attempt snapshot: `attemptRepo.GetLatestForStepAsync(tenantId, operationId, "finalize", ct)` — WorkflowAttemptRepository.cs:45-54, an `.AsNoTracking()` SELECT ordered by `attempt_number` descending, with no row lock and no version. Two guards run before the cancel branch: the idempotent-recovery shortcut (115-186) when the latest attempt is already `Succeeded`/`Reconciled` with a `ProviderRef`, and the Inv-7 guard (196-210) which, when `op.Status == Finalizing` AND the latest attempt is `Dispatching` or `Ambiguous`, CASes `Finalizing → Reconciling` (reason `reconcile_ambiguous`) and returns `Continue`. That guard is deliberately asymmetric — it does not fire from `Held`, because a `Reconciling→Held` no-effect path has already proven no effect (193-195).

The cancel-before-create branch (221-280). The gate at 221-222 is `op.CancellationRequestedAt.HasValue && (latest is null || latest.Outcome == AttemptOutcome.Planned)` — both operands read from the STALE line-89 and line-114 snapshots. The flag itself is monotonic: `RequestCancellationCommandHandler.Handle` (RequestCancellationCommandHandler.cs:39-61) sets it through `SetCancellationRequestedAsync`, whose predicate is `CancellationRequestedAt == null AND NOT TerminalStatuses.Contains(status)` (BookingOperationRepository.cs:110-124), and nothing anywhere clears it — so staleness on the flag is safe in one direction only (it can be newly set, never unset). Staleness on `latest` is NOT safe, which is what the C3 fix was for. Line 224 re-reads `freshOpCancel` outside the transaction and requires `Held` or `Finalizing` (225-226). Line 228 opens the unit of work — `UnitOfWork.ExecuteInTransactionAsync` (UnitOfWork.cs:15-20) calls `BeginTransactionAsync(ct)` with no isolation argument, i.e. PostgreSQL default READ COMMITTED (documented at docs/dotnet-api-patterns.md:153-155). Inside: line 230 re-reads `opInTxn` (again `.AsNoTracking()`, no lock); lines 239-240 re-read `latestInTxn` via the same non-locking `GetLatestForStepAsync`; lines 241-251 return early — committing nothing — if that attempt is now `Dispatching`, `Ambiguous`, `Succeeded` or `Reconciled`. If it is still null or `Planned`, lines 255-267 hop `Held→Finalizing` (reason `finalizing`) and re-read the version, 269-270 re-assert `Finalizing`, and 272-275 CAS `Finalizing → CompensationRequired` with reason `cancelled_before_create`. Line 279 returns `Continue` unconditionally — whether the CAS won, lost, or was skipped by the bail-out.

Where the CAS is actually fenced. Every one of those transitions runs through `BookingOperationRepository.TryTransitionStatusAsync` (61-93), which first calls `OperationStateMachine.EnsureAllowed(expectedStatus, next)` (71) — `Finalizing` permits only `{Booked, Reconciling, CompensationRequired}` (OperationStateMachine.cs:67-72) — and then issues `VersionTokenUpdate.UpdateAsync` (VersionTokenUpdate.cs:33-54), a single `UPDATE booking_operations SET status=…, status_reason=…, updated_at=…, version = version + 1 WHERE tenant_id=… AND operation_id=… AND status=:expected AND version=:expected`. Rows-affected 1 means won, 0 means reload. So the guard is entirely on `booking_operations.version`.

The write that races it, and why the fence misses it. After the cancel branch is skipped, TXN1 (289-364) claims `Held→Finalizing` if needed (301-309, which DOES bump the version), creates-or-loads the `finalize` workflow_step (319-341), and inserts a `Planned` attempt row at `latestAttemptNumber + 1` (346-363); the transaction commits before any external call, per §6.2 line 241. If the circuit is open (372-399) the attempt is marked `Abandoned` and a durable retry is scheduled in one transaction, returning `Reschedule`. Otherwise lines 404-405 execute the dispatch write:

    attempt.Outcome = AttemptOutcome.Dispatching;
    await attemptRepo.UpdateAsync(attempt, ct);

`WorkflowAttemptRepository.UpdateAsync` (32-43) detaches any conflicting tracked instance and calls `db.WorkflowAttempts.Update(attempt); SaveChangesAsync(ct)` — a full-row, unconditional UPDATE of `workflow_attempts` only. It is NOT inside a transaction (`ct`, not a `ct2`), it returns void so a lost race is undetectable, it carries no expected-outcome predicate, and — the crux — it does not touch `booking_operations` at all, so `operation.Version` is unchanged. `workflow_attempts` has no version column to CAS on either: `WorkflowAttemptConfiguration` says so in its own summary ("append-only log; no FK, no version", line 7) and spec 12's column list (12-data-model-and-persistence.md:78) matches. Only `workflow_steps` carries a version (12-…:299).

The window, concretely. Worker A (cancel path) reads `latestInTxn` at 239-240 and sees `Planned`. Worker B, in another driver, executes 404-405 and commits `Dispatching`, then enters `adapter.CreateBookingAsync` (412-414). Worker A, still holding a transaction that took no lock on either row, evaluates 241-251 against its now-stale value, falls through, and CASes at 272-275 on an `operation.version` that B never moved — so the CAS returns 1 row and `Finalizing → CompensationRequired (cancelled_before_create)` wins. A returns `Continue` (279), and A's own driver loop immediately re-dispatches, now seeing `CompensationRequired`, so it sends `CompensateOperationCommand` while B is still inside the provider call.

What each side then writes. B returns from the provider with `Created`/`AlreadyExists` and opens TXN2 (426-582). It commits `attempt.Outcome = Succeeded` with `ProviderRef = result.ProviderReference` and `CompletedAt` (431-434), records circuit success (436), and moves the finalize step `InProgress → Succeeded` (441-447). Then it re-reads the operation at 450-452 and finds `CompensationRequired ≠ Finalizing`, so it returns from the transaction body silently — no `Booked`, no `MaterializeBookedAsync`, no `notification.booking_confirmed.v1` outbox row, no `operation.booked` audit event, no metrics. Post-transaction, 590-592 sees `CompensationRequired` and returns `Continue`. So B's ONLY durable trace of a real external booking is the `provider_ref` on the attempt row.

Meanwhile C (Compensate) runs `CompensateOperationCommandHandler.Handle` (50): it guards `op.Status == CompensationRequired` (57-58), then decides whether an effect exists from ONE unlocked, un-transacted read — `latest = attemptRepo.GetLatestForStepAsync(tenantId, operationId, "finalize", ct); providerRef = latest?.ProviderRef` (64-65) — creates-or-loads the `compensate` step (71-87), and branches. If that read lands AFTER B's TXN2 commits, `providerRef` is present, `adapter.CancelBookingAsync` is called (98), and on acknowledgement the op goes `CompensationRequired → FailedFinal (compensated)` with capacity released — the booking is correctly undone, and the race is benign. If it lands BEFORE B's TXN2 commits — which is the likely ordering, since A's driver dispatches Compensate the instant it returns `Continue` while B is still awaiting the provider — `providerRef` is null and C takes the no-effect branch (217-292): compensate step `→Succeeded`, `CompensationRequired → FailedFinal` with reason `failed_no_effect` (238-241), capacity released (250-251), booking pending-lifecycle reverted (255-256), a `notification.booking_failed.v1` outbox row (259-273) and an `operation.failed_final` audit event (275-286) written, and `StepOutcome.Terminal` returned (292). `FailedFinal` is terminal, so B's later TXN2 guard at 450-452 fails again and nothing re-enters compensation. The customer is told the booking failed; a real reservation sits at the venue with nothing pointing at it. That is the orphaned external booking the issue names, and it violates Inv-7 as owned by spec 06 (docs/specs/README.md:122).

Failure branches that exist on this path today. From the cancel branch: op missing or wrong tenant → `Wait` (91-92); status not Held/Finalizing → `Continue` (94-95); latest attempt already Succeeded/Reconciled with a ref → the idempotent recovery shortcut, which itself splits on `FinalizeAgainstOperationAsync` returning `HoldNoLongerValid` → `CompensationRequired (hold_no_longer_valid)` + audit + `Continue` (139-165, 181-182) versus `Finalized`/`NotTracked` → `Booked` + `MaterializeBookedAsync` + `Terminal` (168-185); latest attempt `Dispatching`/`Ambiguous` while `Finalizing` → `Reconciling (reconcile_ambiguous)` + `Continue` (196-210); the cancel branch's own bail-out on a detected concurrent dispatch → no writes at all, `Continue` (241-251, 279); a lost `Held→Finalizing` race inside the cancel txn → `return` then `Continue` (261-262); a lost `Finalizing→CompensationRequired` CAS → 0 rows, ignored, `Continue` (272-275, 279). From the main path: `txn1Aborted` on a lost claim → `Continue` (366-367); circuit open → attempt `Abandoned` + durable retry scheduled in one transaction → `Reschedule` (372-399); provider `Ambiguous` → attempt `Ambiguous` + `Finalizing→Reconciling (reconcile_ambiguous)` + `RecordFailure` → `Continue` (605-632); `Transient` with budget left → attempt `TransientFailure` + `NextEligibleAt` + a scheduled job written in the same transaction → `Reschedule`, or budget exhausted → `Finalizing→Reconciling (retry_budget_exhausted)` → `Continue` (635-692); `NoCapacity` at finalize (anomalous, §11 has no `Finalizing→AlternativesRequired` edge) → `Finalizing→Reconciling (unexpected_no_capacity)` → `Continue` (697-721); `AuthError`/`PaymentActionRequired` → attempt `Abandoned` + `Finalizing→Reconciling (finalize_auth_error | finalize_provider_action_required)` → `Continue` (733-762); `Rejected`/`PermanentError` → attempt `Rejected` + `Finalizing→CompensationRequired (finalize_permanent_error)` → `Continue` (766-793). Inside the success TXN2 there are three additional exits before `Booked`: op no longer `Finalizing` → silent return (450-452); `CancellationRequestedAt` set after dispatch → `CompensationRequired (cancelled_after_create)` + `operation.cancellation_after_create` audit, no `booking_confirmed` (454-484); `HoldNoLongerValid` → `CompensationRequired (hold_no_longer_valid)` + audit, no `booking_confirmed` (496-527); plus a blank-provider-reference guard (530-531). Any unexpected adapter exception propagates to the driver, which catches `PoisonMessageException`/`InvalidStateTransitionException`, persists a work item + `still_confirming` notification + audit in a committed transaction, then dead-letters the transport message (AdvanceBookingOperationCommandHandler.cs:94-113, Inv-14).

Why the existing guard is only half a fix. `git log -S "FIX (C3)"` attributes the in-transaction re-read to commit 06c6857 "fix(api): address PR #50 review findings (spec 06 concurrency/idempotency hardening)". It closes the window between the line-114 snapshot and the transaction, but not the window between the line 239-240 read and the line 272-275 CAS, because those two statements are fenced on different rows: the read is on `workflow_attempts` (unlocked, versionless) and the CAS is on `booking_operations.version`, which the racing dispatch never advances. Nothing in the codebase currently locks an attempt row; the only `SELECT … FOR UPDATE` precedents are `CapacityHoldRepository.LockAsync` (76-85) and `CapacitySlotRepository.LockAsync` (20-27), both raw SQL selecting a constant behind a documented interface method, and both governed by the global lock-ordering rule at docs/dotnet-api-patterns.md:135-151.

Coverage status. `FinalizeBookingCommandHandlerTests` exists solely as the harness for this wave and says in its own class documentation (lines 25-29) that it deliberately stops at the three pre-transaction guards because the TXN1/TXN2 paths "are exactly the behaviour issues #51, #55, #56, #57 and #58 intend to change". `CompensationAndCancellationTests` Scenario 3 (503-576) and Scenario 3b (578-648) cover cancel-before-create only in the "attempt still null" shape — Scenario 3b is labelled the "FIX (C3) regression guard" and its own comment (583-585) confirms it asserts step 2 as "Find it still null (no concurrent dispatch changed it)". No test in the repository drives the guard's other branch (`latestInTxn` = Dispatching), and no test drives two concurrent workers over this operation. Spec 06 §12 line 421 names "cancellation races creation (FM #13)" as a required §27.3 concurrency test; it is not present.

### Primary files

- **`apps/api/src/Cordia.Application/Handlers/BookingFulfillment/Finalize/FinalizeBookingCommandHandler.cs`** — The file the issue names. The cancel-before-create shortcut re-reads the attempt inside the cancel transaction but the operation CAS it then performs is fenced on `booking_operations.version`, which the concurrent dispatch at 404-405 never touches — so the read at 239-240 and the CAS at 272-275 are not atomic with respect to a concurrent Planned→Dispatching.
- **`apps/api/src/Cordia.Infrastructure/Repositories/WorkflowAttemptRepository.cs`** — This is the exact read the issue calls non-locking, and the exact write that races it. `GetLatestForStepAsync` is documented "AsNoTracking" on the interface (IWorkflowAttemptRepository.cs:20-22). `UpdateAsync` returns void, so a caller cannot detect that it lost a race.
- **`apps/api/src/Cordia.Infrastructure/Repositories/BookingOperationRepository.cs`** — The only write path for booking_operations.status and the only place the operation's version advances. It also shows the cancellation flag is monotonic (set once, never cleared), which is why the stale read at handler line 221 is safe in one direction only.
- **`apps/api/src/Cordia.Infrastructure/EntityFramework/Concurrency/VersionTokenUpdate.cs`** — Proves the issue's premise mechanically: the version bump is owned exclusively by this helper ("so callers cannot forget it"), and the dispatch write does not go through it, so operation.Version is unchanged by Planned→Dispatching.
- **`apps/api/src/Cordia.Infrastructure/EntityFramework/Configurations/WorkflowAttemptConfiguration.cs`** — workflow_attempts carries NO version/concurrency token, so there is no CAS available on the attempt row today. Spec 12 line 78 lists the same column set with no `version`. Any attempt-side fence must therefore be a SELECT … FOR UPDATE or a new column.
- **`apps/api/src/Cordia.Infrastructure/Services/UnitOfWork.cs`** — Establishes the isolation level as PostgreSQL default READ COMMITTED, which is what makes the in-txn re-read a plain point-in-time snapshot with no read lock. docs/dotnet-api-patterns.md:153-155 states this explicitly and forbids raising isolation to fix a race.
- **`apps/api/src/Cordia.Application/Handlers/BookingFulfillment/Compensate/CompensateOperationCommandHandler.cs`** — This is where the race turns into the orphaned external booking. Compensate decides whether an effect exists from one unlocked read of the same attempt row; if it runs before the racing finalize's TXN2 commits the ProviderRef, it takes the null-ref branch and drives the operation to the terminal FailedFinal, after which the finalize TXN2's own guard (handler 450-452) silently returns and nothing ever calls CancelBookingAsync.
- **`apps/api/src/Cordia.Application/Handlers/BookingFulfillment/AdvanceOperation/AdvanceBookingOperationCommandHandler.cs`** — The driver holds no lease or lock on the operation — idempotency is version-guarded transitions only — and StepOutcome.Continue immediately re-loops. So the same driver that commits "cancelled_before_create" dispatches Compensate on the very next iteration, while the racing worker is still inside adapter.CreateBookingAsync.
- **`apps/api/src/Cordia.Application/Handlers/BookingFulfillment/Cancellation/RequestCancellationCommandHandler.cs`** — The producer of CancellationRequestedAt. It performs no status transition (class summary 9-12: "observed at the next workflow checkpoint"), which is why the finalize handler is the sole enforcement point for FM#13.
- **`apps/api/src/Cordia.Domain/Entities/OperationStateMachine.cs`** — Bounds the legal destinations any fix may use. TryTransitionStatusAsync calls EnsureAllowed first, so an illegal edge throws InvalidStateTransitionException and is caught by the driver as a poison/DLQ defect (AdvanceBookingOperationCommandHandler 94-113).
- **`apps/api/src/Cordia.Infrastructure/Repositories/CapacityHoldRepository.cs`** — The in-repo precedent for the issue's second suggested remedy: a lock-only repository method (raw SQL because EF has no FOR UPDATE) that selects a constant, declared on the interface (ICapacityHoldRepository.cs:40-55) with the lock-ordering rationale.
- **`apps/api/src/Cordia.Infrastructure/Messaging/StepSweeperHostedService.cs`** — Concrete proof that a second concurrent driver on the same operation is a real configuration, not hypothetical: OutboxPublisherHostedService, ScheduledJobPollerHostedService and StepSweeperHostedService all run in parallel (MessagingServiceCollectionExtensions.cs:37/41/45) and all three funnel into the same driver command (ApplicationServiceCollectionExtensions.cs:85-96).

### The actual defect, as verified

The defect is real, present at HEAD (aface13), and every factual claim in the issue text checks out against the code. (1) The cancel-before-create branch does re-read the latest attempt inside its transaction — `FinalizeBookingCommandHandler.cs:239-240` — and that read is `WorkflowAttemptRepository.GetLatestForStepAsync` (`:45-54`), a plain `.AsNoTracking()` SELECT with no `FOR UPDATE`; the interface documents it as "AsNoTracking" (`IWorkflowAttemptRepository.cs:20-22`). (2) The transaction is READ COMMITTED — `UnitOfWork.cs:17` calls `BeginTransactionAsync(ct)` with no isolation argument, and a repo-wide grep finds no `IsolationLevel` anywhere — so that read is a point-in-time snapshot holding no read lock. (3) The racing dispatch write at `FinalizeBookingCommandHandler.cs:404-405` goes through `WorkflowAttemptRepository.UpdateAsync` (`:32-43`), which touches only `db.WorkflowAttempts`, runs outside any transaction, and returns `void`; `workflow_attempts` has no version column at all (`WorkflowAttemptConfiguration.cs:7` "append-only log; no FK, no version"; `WorkflowAttempt` has no `Version` property; spec 12 §78 matches), and there are no DB triggers. So Planned→Dispatching provably leaves `booking_operations.version` untouched — the version bump is owned exclusively by `VersionTokenUpdate.UpdateAsync` (`:41-52`, "The version bump is owned by this helper so callers cannot forget it"), which the dispatch write never calls. (4) The CAS at `:272-275` is therefore fenced on a version the racing worker never moved, wins its 1 row, and commits `Finalizing → CompensationRequired (cancelled_before_create)`. (5) The consequence is reachable: the driver holds no lease on the operation ("idempotency comes from version-guarded transitions, not from inbox suppression", `AdvanceBookingOperationCommandHandler.cs:55-56`), re-loops immediately on `Continue` (`:90-91`), and routes `CompensationRequired → CompensateOperationCommand` (`:163-164`); `StepSweeperHostedService` and `ScheduledJobPollerHostedService` each publish straight into that driver from their own loop threads (`StepSweeperHostedService.cs:93`, `ScheduledJobPollerHostedService.cs:104`, both registered at `MessagingServiceCollectionExtensions.cs:37/41/45`), so two concurrent finalize handlers on one operation is an ordinary configuration. Compensate then decides whether an effect exists from ONE unlocked, un-transacted read (`CompensateOperationCommandHandler.cs:64-65`) and, finding `providerRef` null while the racing worker is still inside `adapter.CreateBookingAsync`, drives the op to terminal `FailedFinal (failed_no_effect)` (`:238-241`), releases capacity (`:250-251`) and emits the customer-facing failure (`:259-273`). The racing worker's TXN2 then commits the real `ProviderRef` (`:431-434`) but bails silently at `:450-452`, so nothing ever calls `CancelBookingAsync`. Orphaned external booking, exactly as stated. TWO REFINEMENTS the issue understates, both worth carrying into the fix. First, the named window is the narrower of two: because TXN1 performs NO version-guarded write on the operation when it is already `Finalizing` (`:299-315` — the `else if (current.Status != OperationStatus.Finalizing)` arm just aborts, and the Finalizing case falls through with no CAS), a cancel-CAS committing anywhere between TXN1's op read at `:291` and the provider call at `:412` produces the identical orphan with NO stale read at all — the cancel worker legitimately sees no attempt row because the racing TXN1 has not committed yet. That sibling window is several DB round trips wide, whereas the window the issue names is microseconds (the circuit-breaker check between TXN1 commit and the dispatch write is in-memory, `InMemoryProviderCircuitBreaker.cs:38`). The root cause is best stated as: the finalize worker holds no fence on `booking_operations` across the entire span from TXN1 to TXN2, so the operation can leave `Finalizing` while the external call is in flight and the worker only discovers it after the booking exists. Second, of the two remedies the issue proposes, only the first works. Bumping `operation.Version` on Planned→Dispatching closes both windows, but ONLY if implemented as a version-guarded conditional UPDATE whose rows-affected the dispatcher checks and treats as abort-before-provider-call (§22.1, spec 06:304) — a bare bump is not enough. "SELECT FOR UPDATE the attempt in the cancel txn" does NOT close it: locking the attempt row merely makes the racing `UpdateAsync` at `:405` block until the cancel txn commits, after which it proceeds to set Dispatching and call the provider anyway, because nothing between TXN1 and the provider call re-reads the operation status; and in the sibling window there is no attempt row to lock. Finally, the orphan is contingent on a second race — if Compensate's read at `:64-65` lands after the racing TXN2 commits `ProviderRef`, the providerRef-present branch (`:96-98`) cancels correctly and the race is benign — but that ordering is unlikely, since the cancel worker dispatches Compensate within milliseconds while the racing worker is still awaiting a network call. No later commit fixes this: `git log` on the handler shows the last concurrency change is 06c6857 (the "FIX (C3)" in-txn re-read this issue calls residual), and the code at HEAD is unchanged. No test drives the guard's other branch — `cancelled_before_create` appears nowhere under `apps/api/test`, and `FinalizeBookingCommandHandlerTests` says in its own doc that it stops before TXN1/TXN2 "because those are exactly the behaviour issues #51, #55, #56, #57 and #58 intend to change". Spec 06 §12 line 421 requires a §27.3 concurrency test for "cancellation races creation (FM #13)"; it does not exist.

Otherwise one transaction (161-264) writes: the existing attempt updated to Outcome=Reconciled with ProviderRef, CompletedAt and a Reconciliation JSON blob {resolved_by:"lookup", via, provider_reference} (164-178), or a synthesized att_… row with AttemptNumber=1 and Outcome=Reconciled when no attempt existed (183-201); the finalize step InProgress→Succeeded (205-210); a version-guarded op transition Reconciling→Booked with reason "reconciled_booked" and bookingId=r.ProviderReference (213-221); and, only if that transition affected rows, an outbox row whose MessageType is PreorderSagaMessages.ConfirmedOutcomeType(freshOp.IsPreorder) with payload {operation_id, booking_id, tenant_id} (227-241), an audit event "operation.reconciled" with {booking_id, resolution_path=via, provider} (243-259), and two counters (260-261). Returns StepOutcome.Terminal (266), which stops the driver loop.

No-effect branch (269-343) — the branch the issue is about. It computes latestAttemptNumber = latest?.AttemptNumber ?? 1 (272) and firstAttemptAt = step?.CreatedAt ?? UtcNow (273), then calls retryPolicy.NextEligibleAt(StepRetryBudget.ForCreateBooking, …) (276-280). ForCreateBooking is 4 attempts / 10 minutes elapsed / 1 s base / 30 s cap (StepRetryBudget.cs:67-68), and FullJitterRetryPolicy returns null when completedAttemptNumber >= MaxAttempts or elapsed >= MaxElapsed (FullJitterRetryPolicy.cs:26-31). The returned timestamp itself is DISCARDED — only its nullness is read. Nothing is scheduled: no scheduled_jobs row, no NotBefore, no back-off. Contrast FinalizeBookingCommandHandler.cs:681-682, which passes its own NextEligibleAt value to RetryScheduler.ScheduleAsync inside the outcome transaction.

  • Budget exhausted (nextEligible == null, 282-309): re-read the op outside a transaction (287), and if still Reconciling open a transaction, re-read for a consistent version, and call ManualReviewEscalator.EscalateAsync with reason "reconcile_no_effect_budget_exhausted" and slaDeadline = now + 1 hour (290-305). The escalator (ManualReviewEscalator.cs:34-110) performs the version-guarded Reconciling→ManualReview transition, and only on rows>0 writes an open operations_work_items row via TryAddOpenAsync, a notification.still_confirming.v1 outbox row, and an "operation.manual_review" audit event, all inside the caller's transaction. Handler returns StepOutcome.Wait (308), so the driver breaks out of its loop; nothing else drives the op until a booking.reconcile.requested.v1 / booking.step.continue.v1 / booking.command.requested.v1 message arrives or an operator acts.

  • Budget remains (311-343): re-read the op (316) and, if still Reconciling, open ONE transaction that (a) re-reads the latest "finalize" attempt and, if its Outcome is Dispatching or Ambiguous, rewrites it to Abandoned with CompletedAt=now (323-329) — explicitly so FinalizeBookingCommandHandler's Inv-7 guard will not block the re-create — and (b) performs the version-guarded transition Reconciling→Held with reason "reconcile_no_effect_recreate" (331-339). Nothing else is written: no audit event, no metric, no work item, no notification. The handler returns StepOutcome.Continue (343).

What Continue costs. The driver does not stop: it reloads the op in the same for-loop (AdvanceBookingOperationCommandHandler.cs:76), sees Held, and dispatches RequestPaymentCommand. On a no-deposit op RequestPaymentCommandHandler takes the fast path Held→Finalizing with reason "finalizing" and returns Continue (RequestPaymentCommandHandler.cs:53-85); the driver reloads again, sees Finalizing, and dispatches FinalizeBookingCommand. There, the idempotent-success shortcut does not apply (the attempt is Abandoned, not Succeeded/Reconciled — FinalizeBookingCommandHandler.cs:115), and the Inv-7 in-flight guard is disarmed twice over: it only fires for Dispatching/Ambiguous attempts, and only when op.Status == Finalizing having arrived there by another route (196-197; the comment at 193-195 states the assumption outright — "When op.Status == Held after a Reconciling→Held no-effect path, the reconcile handler has already proven no effect exists"). TXN1 then GetOrAdds the finalize step, inserts a fresh Planned attempt at AttemptNumber+1 (289-364), the attempt is marked Dispatching (404-405), and adapter.CreateBookingAsync is invoked with the SAME provider idempotency key (412-414). That is the second submission: on a provider that honours the key it returns AlreadyExists and is harmless; on a provider whose reconciliation API was merely unavailable — the exact condition that produced the Transient lookup — it is a real second create.

So on the issue's scenario the observable behaviour is: op Reconciling, LookupByIdempotencyKeyAsync returns Transient (or Ambiguous, or AuthError), `via` stays "idempotency_key", the reference and status rungs are skipped because r.Kind != NotFound, effectProven is false, the budget check passes at attempt 1 of 4 with elapsed measured from step.CreatedAt, the prior Dispatching/Ambiguous attempt is stamped Abandoned, the op moves Reconciling→Held with reason "reconcile_no_effect_recreate", and within the same message dispatch the provider receives another CreateBookingAsync. The whole cycle repeats — each pass adding one attempt row via Finalize's TXN1 — until either MaxAttempts=4 or the 10-minute elapsed budget from step.CreatedAt trips NextEligibleAt to null, at which point the next reconcile pass escalates to ManualReview. Nothing in the durable record distinguishes "provider confirmed the booking is absent" from "we could not reach the provider's lookup": both produce the same Held transition with the same reason string, no audit event and no metric, which is precisely what §19.2 ("Giving up is an event, not a silence") and §19.1 ("the failure mode of a duplicated state set is silence") warn against.

Why no test catches it. Every lookup stub in the repo returns only NotFound or AlreadyExists: StubBookingProviderAdapter.cs:40-64, the integration FakeBookingProviderAdapter at ReconciliationTests.cs:55-70, and every Moq setup in ReconcileOperationCommandHandlerTests.cs. There is no test at any level in which a lookup returns Transient, Ambiguous, AuthError or PermanentError, and no unit test of the "reconcile_no_effect_budget_exhausted" escalation for a Create operation.

### The actual defect, as verified

Every literal code claim in the issue checks out — the `?? now.AddSeconds(30)` swallow is at FinalizeBookingCommandHandler.cs:378-382, it is the only NextEligibleAt call site in apps/api/src that discards the null, the transient branch does route null to Reconciling/"retry_budget_exhausted" (639-643, 660-673), commit 06c6857 IS an ancestor of HEAD and left the fallback untouched (it appears as an unchanged context line in that commit's hunk `@@ -282,23 +303,28 @@`), and nothing else can move a Finalizing op to ManualReview (OperationStateMachine.cs:67-72 gives Finalizing only {Booked, Reconciling, CompensationRequired}; the SLA evaluator explicitly "Does NOT transition OperationStatus", EvaluateOperationSlaCommand.cs:17). But the issue misattributes the root cause and its prescribed fix would make things worse. (1) ROOT CAUSE IS ONE LAYER UP: the circuit check at line 372 runs AFTER TXN1 has already allocated a fresh attempt number (`AttemptNumber = latestAttemptNumber + 1`, line 357, over `GetLatestForStepAsync` which orders by AttemptNumber desc). So a circuit-open pass — which makes NO provider call — still burns one unit of a MaxAttempts=4 budget. With jitter caps of [0,2s)/[0,4s)/[0,8s) the attempt budget is fully consumed within roughly 7-14 seconds, i.e. before the breaker's default 30 s openDuration has elapsed even once. The "budget exhaustion" the issue wants to escalate on is an artefact of charging the budget for calls that were never dispatched, which contradicts §15.3 ("Track both: attempt count; total elapsed time since the step first became eligible"). (2) THE ISSUE MISSES THE WORSE, FAR MORE COMMON FAILURE MODE — the mirror image of the one it describes. After only three circuit-open passes the op is at AttemptNumber 4. When the breaker half-opens and hands this op the single probe (InMemoryProviderCircuitBreaker.cs:128-132), the create runs, returns Transient, and the transient branch computes NextEligibleAt(budget, 4, ...) → null → immediately transitions Finalizing→Reconciling "retry_budget_exhausted" → ManualReview. A routine 30-second provider blip therefore dumps in-flight bookings onto a human after ONE real provider attempt, having never delivered the four retries §15.3 budgets. That is premature escalation, not delayed escalation, and it fires on the ordinary case rather than the pathological one. (3) THE SUGGESTED FIX IS HARMFUL: escalating on null inside the circuit-open branch would trip at ~10 s of outage, before the first half-open probe, and the escalation path runs straight into ReconcileOperationCommandHandler, which contains no circuitBreaker reference at all and unconditionally walks the §16.2 ladder against the provider just declared unhealthy (LookupByIdempotencyKeyAsync:116, LookupByReferenceAsync:121, GetStatusAsync:127). That directly violates FM#10 / §15.4 "stop flooding it with retries" — the very property Test 4 `CircuitOpen_NoProviderFlood_DurableRetryScheduled` asserts with `Assert.Equal(0, fakeAdapter.CreateCallCount)` — and spec 06 §6.3 draws `CircuitOpen --> StepEligible: keep job scheduled, probe recovery` with no BudgetExhausted arc out of CircuitOpen. The observable symptom the issue reports (unbounded 30 s cycling under a sustained or flapping outage, one Abandoned workflow_attempts row and one fresh-JobId scheduled_jobs row per cycle, op.UpdatedAt frozen because TryTransitionStatusAsync is the only writer of it) is real and does occur, but it is the second-order consequence. The correct remedy is to stop counting undispatched attempts: move the circuit check ahead of the TXN1 attempt insert, or exclude circuit-abandoned attempts from the budget count. Once attempts are counted honestly the attempt arm can never fire from circuit-open passes, leaving only the 10-minute elapsed arm as a null source — where escalating per FM#11 is defensible and coincides with the sla_escalation work item the SLA evaluator already opens at 600 s. Note also that the single-operation case does self-terminate (the lone op wins the half-open probe within ~30-60 s); the "forever" in the title requires many operations contending for one probe per 30 s window, which the issue's own closing note half-concedes.

Finalize entry guards. `FinalizeBookingCommandHandler.Handle` (FinalizeBookingCommandHandler.cs:87) loads the op with `opRepo.GetAsync` — which carries no tenant predicate (BookingOperationRepository.cs:32-35) — and returns `Wait` if it is null or foreign (91-92), `Continue` if the status is anything other than `Held` or `Finalizing` (94-95). It derives the stable provider idempotency key from `(operationId, "finalize", op.IntentRevision)` (101) and loads the intent revision for `requestHash` and `canonicalPayload`, defaulting to `""`/`"{}"` when absent (104-106).

THE RECOVERY SHORTCUT (108-186) — the path the issue is about. Line 114 reads the latest attempt for the finalize step. Line 115 tests `latest is { Outcome: AttemptOutcome.Succeeded or AttemptOutcome.Reconciled } && latest.ProviderRef is not null`. If that holds, the handler never calls the provider again and never reaches the Inv-7 guard (196-210), the FM#13 cancel-before-create guard (221-280), TXN1 (289-364) or the success TXN2 (419-601) — all of those are below it in the method.

Inside the shortcut it re-reads the op (118) and only acts when the status is still `Finalizing` (119). It then opens one transaction (125-179) and re-reads the op INSIDE that transaction as `current2` (127), bailing if it is null or no longer `Finalizing` (128-129). It calls `capacityReservation.FinalizeAgainstOperationAsync(tenantId, operationId, "create", ct2)` (136-137) — the single capacity decision point (ICapacityReservation.cs:69-96). On `HoldNoLongerValid` it writes `Finalizing → CompensationRequired` with reason `"hold_no_longer_valid"` (143-146), and when that CAS affects a row it sets a local `recoveryHoldExpired` flag and appends an `operation.hold_no_longer_valid` audit event with `hold_id = null` (148-163), then returns from the transaction body without booking (164). On `Finalized` or `NotTracked` it falls through and issues `opRepo.TryTransitionStatusAsync(tenantId, operationId, current2.Version, Finalizing, Booked, reason: "booked", bookingId: latest.ProviderRef)` (168-171); if that affects a row it calls `bookingRepo.MaterializeBookedAsync` with an aggregate built by `BuildBookingAggregate` (175-177, 844-890), which inserts or updates the `bookings` row to `LifecycleStatus = Confirmed`, clears `PendingOperationId`, and sets `BookingId = ProviderReference` (BookingRepository.cs:19-41).

After the transaction, if `recoveryHoldExpired` it returns `StepOutcome.Continue` so the driver picks up the now-`CompensationRequired` op (181-182). Otherwise it calls `ExtendContactRetentionAsync` best-effort outside any transaction (184, 809-842) and returns `StepOutcome.Terminal` (185), which breaks the driver loop.

THE ASYMMETRY. `op.CancellationRequestedAt` appears nowhere between lines 114 and 186. The shortcut re-reads the operation twice (118 and 127) and already carries a not-Booked routing branch (139-165), but it consults only capacity. The main success TXN2 does the opposite: after writing the attempt `Succeeded` with its `ProviderRef` (431-434) and moving the finalize step `InProgress → Succeeded` (441-447), it re-reads the op (450-452) and, when `currentOp.CancellationRequestedAt.HasValue` (454), writes `Finalizing → CompensationRequired` with reason `"cancelled_after_create"` (458-461), appends an `operation.cancellation_after_create` audit event carrying `provider_ref` (465-480), and returns early with the explicit comment `// do NOT emit booking_confirmed` (483). Only after that check does it consult capacity (493-527) and only then transition to `Booked` (533-536). The Reconcile handler applies the same rule from its side: on a proven effect with a cancellation pending it escalates `Reconciling → ManualReview` with reason `"cancel_raced_reconciled_booking"` and returns `Wait` (ReconcileOperationCommandHandler.cs:134-158). The shortcut is the one Finalizing→Booked write in the codebase that skips this.

REACHABILITY OF `attempt = Succeeded` WITH `op = Finalizing`. Inside success TXN2 the attempt update (431-434) and the `Finalizing → Booked` CAS (533-536) are in the same transaction, but the CAS is version-and-status-guarded (`VersionTokenUpdate.UpdateAsync`, VersionTokenUpdate.cs:33-54: `WHERE key AND version = expected`, returning 0 rows on a lost race). `currentOp` is read at 450 and its `Version` is passed at 534; any write that bumps the row's version between those points — including `SetCancellationRequestedAsync`, which does its own `ExecuteUpdateAsync` (BookingOperationRepository.cs:110-124) — makes the CAS return 0. The transaction still commits: the attempt row is `Succeeded` with a `ProviderRef`, the finalize step is `Succeeded`, and the op stays `Finalizing`. The post-txn re-read (590-592) sees `Finalizing`, which is neither `CompensationRequired`/`Reconciling` nor `Booked`, so it falls to `return StepOutcome.Terminal` at 600 without extending contact retention. The finalize `workflow_step` is now `Succeeded`, but the operation is not terminal; a re-delivery of `booking.command.requested.v1`, or any later `AdvanceBookingOperationCommand` on that operation, re-enters Finalize, and line 115 now matches. (The `StepSweeperHostedService` re-enqueue path at StepSweeperHostedService.cs:47-119 only lists NON-terminal steps, so in this particular variant the sweeper is not the re-driver; a plain redelivery or any subsequent driver dispatch is.) The `Reconciled` half of the predicate is reachable the same way from Reconcile's effect-proven branch.

WHAT HAPPENS WHEN A CANCELLATION IS PENDING AT THAT MOMENT. `RequestCancellationCommandHandler.Handle` (RequestCancellationCommandHandler.cs:24-64) sets `CancellationRequestedAt` and writes an `operation.cancellation_requested` audit event in one transaction; it performs no status transition (class doc 9-12 — "observed at the next workflow checkpoint"). Its repository predicate only fires while `CancellationRequestedAt IS NULL AND status NOT IN (terminal)` (BookingOperationRepository.cs:117-120). On the next re-drive, the shortcut fires, ignores the flag, and writes `Finalizing → Booked` (168-171). `OperationStateMachine.EnsureAllowed` accepts it — `Finalizing` legally reaches `Booked`, `Reconciling` and `CompensationRequired` (OperationStateMachine.cs:67-72) — so nothing at the repository or state-machine layer objects (BookingOperationRepository.cs:71). The op is now `Booked`, which is terminal (derived at OperationStateMachine.cs:118-121), the `bookings` row is materialized `Confirmed`, `booking_operations.booking_id` is set to the provider reference, and `status_reason` reads `"booked"`. The handler returns `Terminal`, so the driver's loop breaks (AdvanceBookingOperationCommandHandler.cs:90-91) and `CompensateOperationCommand` is never dispatched — even though `CompensateOperationCommandHandler` reads its `providerRef` from exactly the same latest finalize attempt (CompensateOperationCommandHandler.cs:64-65) and would have called `CancelBookingAsync` on it (98). Any later cancel attempt now returns 0 rows because the op is terminal. `GetOperationStatusQuery` reports `terminal = true` and the flat message "Your booking is confirmed." (GetOperationStatusQuery.cs:66-79, 109), and the `cancellation_pending` wording — which is only produced for non-terminal ops (91-94) — stops being surfaced. The guest's cancellation is silently discarded and the venue keeps the reservation.

THE SECONDARY GAP. The shortcut's Booked branch writes no outbox row at all. The main TXN2 emits the confirmed-outcome message inside the same transaction as the Booked CAS (547-561, type chosen by `PreorderSagaMessages.ConfirmedOutcomeType(currentOp.IsPreorder)` → `notification.booking_confirmed.v1` or the pre-order saga's `booking_committed`), plus an `operation.booked` audit event (563-578) and the `FulfillmentAcceptedToBookedMs` / `FulfillmentOperationTerminalTotal` metrics (579-580). The shortcut emits none of these. Grepping the source confirms the only other producers of `notification.booking_confirmed.v1` are `ResolveManualReviewCommandHandler`, the pre-order commit handler and the waitlist accept handlers — none of which run here. The one thing that notices is `AuditMissingTerminalNotificationCommandHandler`, which for a `Booked` op expects `NotificationEvent.BookingConfirmed` (28-32) and raises an `operations_work_items` row with reason `"missing_notification"` (71-80) while explicitly not mutating `booking_operations` (class doc 15-16). So the outcome is an operator alert, never a customer confirmation — the operation ends `Booked`, terminal, with no notification and, in the cancellation case, against the guest's explicit request.

OTHER FAILURE BRANCHES ON THIS PATH. (a) If the shortcut's Booked CAS loses its own version race (`bookedRows == 0`, 173), nothing is written — no booking materialized — yet the handler still falls through to `ExtendContactRetentionAsync` (184) and returns `Terminal` (185), so the driver stops with the op still in `Finalizing`. (b) If `fresh` is non-null but its status is `Held` rather than `Finalizing` (possible after a `Reconciling → Held` no-effect path), the whole transaction is skipped and the handler returns `Terminal` at 185 having done nothing. (c) The shortcut never touches `stepRepo`, so it leaves the finalize `workflow_step` at whatever status it had. (d) `ExtendContactRetentionAsync` swallows every exception with a warning (830-841) — deliberate, since the booking is already committed. (e) Unexpected adapter or repository exceptions of type `PoisonMessageException` / `InvalidStateTransitionException` propagate to the driver's catch (AdvanceBookingOperationCommandHandler.cs:94-113), which persists a work item, a deterministic `notification.still_confirming.v1` outbox row and an `operation.poison_quarantined` audit event before dead-lettering the transport message; the operation keeps its business state (Inv-14).

SPEC POSITION. Design §15.5 (booking-agent-reliability-design.md:1588-1597) states that workers "check cancellation and current version before each side effect", and that when cancellation races an external create the engine must "reconcile the create result; cancel or compensate if creation succeeded; expose cancellation_pending until the outcome is known". Spec 06 FM#13 (06-booking-workflow-and-fulfillment.md:342) restates it as the required recovery. Spec 06 §7 line 300 ties the `→Booked` transition and the `notification.booking_confirmed` outbox row together as Inv-8. The recovery shortcut satisfies neither: it performs the side effect (confirming the booking) without the cancellation check §15.5 requires, and it performs the `→Booked` transition without the outbox row §7/Inv-8 pairs with it.

### The actual defect, as verified

The routing defect is real and present at HEAD (aface13), exactly where the issue says: `ProviderResultKind.NotFound` returned from `adapter.CreateBookingAsync` matches none of the five guarded arms in the TXN2 dispatch chain (Created/AlreadyExists 419, Ambiguous 605, Transient 635, NoCapacity 697, AuthError/PaymentActionRequired 733), so it falls into the unguarded block at 764-793 whose own comment says "TXN2 (Rejected / PermanentError)". There, `_ => AttemptOutcome.Abandoned` (772) catches it, `classifier.Classify(result).Classification` writes `Ambiguous` onto the attempt row (774), and the op is CASed `Finalizing → CompensationRequired` with reason "finalize_permanent_error" (785-788). The whole 985-line file contains zero occurrences of the token `NotFound`, and `06c6857` (the AuthError/PaymentActionRequired fix the issue cites) is the last commit to touch this routing — nothing later fixed it. The contradiction with `RetryClassifier.cs:34` (`NotFound => new RetryDecision(RetryClassification.Ambiguous, RetryAction.ManualReview)`) is genuine and is pinned by `RetryClassifierTests.cs:19`.

WHERE THE ISSUE IS WRONG — and it is wrong about the harm, which is the part that sets severity. The issue says routing to CompensationRequired "then attempts to compensate a booking whose effect is unprovable (and whose provider ref may be unknown)". No compensation is ever attempted, and the provider ref is not "may be unknown" — it is deterministically null. `attempt.ProviderRef` is assigned at exactly one place in the handler, line 432, inside the Created/AlreadyExists branch; the catch-all never touches it. `GetLatestForStepAsync` orders `OrderByDescending(a => a.AttemptNumber)`, so Compensate reads the very attempt just written. Therefore `CompensateOperationCommandHandler` line 96 `if (providerRef is not null)` is always false on this path, branch 4a (`CancelBookingAsync`) is unreachable, and branch 4b runs unconditionally: `CompensationRequired → FailedFinal` reason "failed_no_effect" (238-241), `ReleaseByOperationAsync(..., ReleaseReason.Compensated)` (250-251), `BookingPendingLifecycle.RevertOnFailureAsync` (255-256), a `notification.booking_failed.v1` outbox row carrying `reason = "failed_no_effect"` (259-273), and an `operation.failed_final` audit event. Because the finalize handler returns `StepOutcome.Continue` (793) and the driver loops on `Continue` (AdvanceBookingOperationCommandHandler 89-91, dispatching CompensationRequired → CompensateOperationCommand at 163-164), all of this completes inside ONE message dispatch.

So the true defect is not "we try to undo a booking we cannot prove exists". It is: the platform asserts to the customer that no booking was made, releases the capacity hold, and terminalizes the operation — without ever performing a single provider lookup — for an outcome its own classifier records, in the same transaction, as `Ambiguous`. `LookupByIdempotencyKeyAsync`/`LookupByReferenceAsync`/`GetStatusAsync` are reachable only from ReconcileOperationCommandHandler, which this path never enters; no work item is opened, no `still_confirming` notification is emitted, ManualReview is never entered, and there is no operator-visible pause between Finalizing and FailedFinal. That is strictly worse than "attempts to compensate" — a compensate call would at least have probed the provider.

Three smaller inaccuracies. (a) The cited line numbers are stale: the catch-all is 764-793, not "~623-652"; the AuthError branch is 733-761, not "~592-621". (b) "every ProviderResultKind ... is explicitly handled except NotFound" is loose — `Rejected` and `PermanentError` are also unguarded; the block is a deliberate catch-all for those two into which NotFound silently falls. (c) The suggested fix's stated effect overstates: routing NotFound to Reconciling does NOT resolve it to ManualReview. Reconcile's §16.2 steps 2 and 3 are gated on `latest?.ProviderRef is not null` (119, 125), so with a null ref only the key lookup runs; with no effect proven it consults `StepRetryBudget.ForCreateBooking` (4 attempts / 10 min) and, not being exhausted on attempt 1, takes `Reconciling → Held` reason "reconcile_no_effect_recreate" (334-338) and re-creates under the same key. ManualReview arrives only after the budget is spent (282-309). That is still spec-sanctioned (§6.2 "re-create allowed under SAME provider key; or →ManualReview if not uniquely provable") but it is a re-create loop, not the immediate escalation the issue implies.

On reachability, the issue's "low likelihood / adapter contract violation" framing is defensible but weaker than stated: `StubBookingProviderAdapter.CreateBookingAsync` (24-36) returns only AlreadyExists or Created, so no shipped adapter and no existing test can hit the branch. But `IBookingProviderAdapter.CreateBookingAsync` documents no restriction on returned kinds ("Create a new booking at the provider using a stable idempotency key (Inv-2/3)."), a real 404-from-create (unknown service/resource id) is an ordinary provider response, and the codebase already anticipates NotFound from a non-lookup call — `ModifyBookingCommand.cs:181-193` handles it explicitly. Also worth noting: `RetryAction` is consumed nowhere in `apps/api/src` (only produced by the classifier and asserted in its test), so the classifier's "authority" is advisory — but the `Ambiguous` classification IS durably persisted at 774, which makes the contradiction a real data-level one, not merely a philosophical one.

### What the code does today

## Part 1 — the reconcile lane is capacity-blind

**How an operation gets there.** The fulfilment driver is purely status-driven: `AdvanceBookingOperationCommandHandler.StepCommandFor` (AdvanceBookingOperationCommandHandler.cs:129-169) maps `OperationStatus.Reconciling` → `ReconcileOperationCommand` at lines 161-162, with no knowledge of whether the operation holds first-party capacity.

An operation becomes first-party-tracked in `ReserveCapacityCommandHandler.Handle` (ReserveCapacityCommandHandler.cs:48-290). It parses the intent revision's canonical payload into `(requestedCapacity, capacityIsExplicit, slotId)` via `CapacitySlotKey.DeriveFromCanonicalPayload` (lines 63-65), and inside one transaction sets `isTracked = slotId is not null && capacityToReserve > 0 && await slotRepo.GetAsync(tenantId, slotId, ct2) is not null` (lines 135-137). On the tracked branch `FirstPartyCapacityReservation.ReserveAsync` (FirstPartyCapacityReservation.cs:56-147) performs the §4.3 conditional `UPDATE capacity_slots SET held_capacity = held_capacity + N WHERE total - held - booked >= N` (99-117) and INSERTs an `Active` `capacity_holds` row keyed `(operation_id, workflow_step="create")` (131-146); `CapacityExpiryScheduler.ScheduleAsync` then writes a durable `booking.scheduled.hold_expiry.v1` job with the deterministic id `sj_holdexp_{holdId}` and `RunAfter = now + CapacityOptions.HoldTtl` (45 minutes), and the op moves `ReservingCapacity → Held` — all in the same transaction (lines 155-173). The untracked branch (lines 240-286) transitions straight to `Held` with no hold and counts `FulfillmentCapacityUntrackedTotal{reason = no_slot_key | slot_not_declared}` (276-283).

Nothing between that reserve and `FinalizeBookingCommandHandler`'s TXN2 ever finalizes the hold. Five live routes park such an operation in `Reconciling` with its hold still `Active`:

- FinalizeBookingCommandHandler.cs:196-210 — the Inv-7 guard: op is `Finalizing` and the latest attempt is `Dispatching`/`Ambiguous` → `Finalizing → Reconciling`, reason `reconcile_ambiguous`.
- :605-632 — provider returned `Ambiguous` → `Reconciling`, reason `reconcile_ambiguous`.
- :660-673 — transient retry budget exhausted → `Reconciling`, reason `retry_budget_exhausted`.
- :697-721 — `NoCapacity` at finalize (anomalous; §11 has no `Finalizing → AlternativesRequired` edge) → `Reconciling`, reason `unexpected_no_capacity`.
- :733-762 — `AuthError` / `PaymentActionRequired` → `Reconciling`, reasons `finalize_auth_error` / `finalize_provider_action_required`.

(`ReserveCapacityCommandHandler`:229-237 also maps `ReservationStatus.Ambiguous → Reconciling`, but that arm is unreachable today: `FirstPartyCapacityReservation.ReserveAsync` only ever returns `Held` or `NoCapacity`, and `CapacityPrimitiveResolver.Resolve` hardcodes `FirstParty` with no external adapter wired.)

**What the handler then does.** `ReconcileOperationCommandHandler`'s primary constructor (ReconcileOperationCommandHandler.cs:33-43) takes exactly ten dependencies — `IBookingOperationRepository`, `IWorkflowStepRepository`, `IWorkflowAttemptRepository`, `IOutboxRepository`, `IAuditEventRepository`, `IBookingProviderAdapter`, `IRetryPolicy`, `ManualReviewEscalator`, `IUnitOfWork`, `Metrics`. There is no `ICapacityReservation`, no `ICapacityHoldRepository`, no `ICapacitySlotRepository`, and no `IBookingRepository` anywhere in the file. A repo-wide grep for `FinalizeAgainstOperationAsync` in `apps/api/src` returns only FinalizeBookingCommandHandler:136 and :493, ResolveManualReviewCommandHandler:290, ModifyBookingCommand:454 and ModifyCapacitySettlement:112 — reconcile is absent from that list.

`Handle` (49-344) runs:

1. Loads the op; `null` or wrong tenant → `StepOutcome.Wait` (51-54); status not `Reconciling` → `Continue` (56-57).
2. A `Cancel`/`Modify`/`Reschedule` op is escalated to `ManualReview` (reason `cancel_reconcile_requires_review` or `modify_reconcile_requires_review`, SLA `now + 30 min`) and returns `Wait` (79-102) — the create-shaped lookup cannot prove those outcomes. So only `Create` operations reach the ladder.
3. Derives the provider key: `step?.ProviderIdempotencyKey ?? latest?.ProviderIdempotencyKey ?? ProviderIdempotencyKey.Derive(operationId, "finalize", op.IntentRevision)` (105-110).
4. Runs the §16.2 ladder against `ProviderAccount = "default"`: `LookupByIdempotencyKeyAsync`, then `LookupByReferenceAsync` if the first returned `NotFound` and `latest?.ProviderRef` is non-null, then `GetStatusAsync` under the same condition; `via` records which rung answered (116-129).
5. `effectProven = r.Kind is Created or AlreadyExists && r.ProviderReference is not null` (131-132).

**Effect-proven branch (134-267) — the gap.** If `op.CancellationRequestedAt` is set, FM#13 escalates to `ManualReview` with reason `cancel_raced_reconciled_booking` and returns `Wait` (139-158). Otherwise a single `uow.ExecuteInTransactionAsync` (161-264) writes:

- the reconciled attempt row — either updating `latest` to `Outcome = Reconciled`, `ProviderRef = r.ProviderReference`, `CompletedAt = now`, `Reconciliation = {"resolved_by":"lookup","via":…,"provider_reference":…}` (171-179), or inserting a fresh `WorkflowAttempt` with `AttemptNumber = 1`, `RequestHash = ""`, `RequestMeta/ResponseMeta = "{}"` when no attempt row existed (180-202);
- the `finalize` workflow step `InProgress → Succeeded` (205-210);
- a version-guarded `TryTransitionStatusAsync(Reconciling → Booked, reason "reconciled_booked", bookingId: r.ProviderReference)` after re-reading the op inside the transaction (213-222);
- and, only if that returned `rows > 0`, an outbox row of type `PreorderSagaMessages.ConfirmedOutcomeType(freshOp.IsPreorder)` (i.e. `notification.booking_confirmed.v1`, or the saga signal for a pre-order) carrying `{operation_id, booking_id, tenant_id}` (227-241), an `operation.reconciled` audit event with `{booking_id, resolution_path, provider}` (243-259), and the counters `FulfillmentReconciliationTotal{result=via}` and `FulfillmentOperationTerminalTotal{state=booked}` (260-261).

Returns `StepOutcome.Terminal` (266).

What that transaction does **not** contain: any call to `ICapacityReservation.FinalizeAgainstOperationAsync`, so no `capacity_holds` row is flipped `Active → Finalized` and no `capacity_slots` row moves units `held → booked`. It also does not call `bookingRepo.MaterializeBookedAsync` — the only two call sites of that method in the whole solution are FinalizeBookingCommandHandler:175 and :540 — so an operation booked by reconcile has no `bookings` aggregate row either.

**The two concrete outcomes today.**

*(a) Hold still Active when reconcile runs.* The op reaches `Booked`, the hold stays `Active`, the slot still counts the units as `held` and `booked_capacity` is never incremented. The expiry job scheduled at reserve time later fires `ReleaseExpiredHoldsCommandHandler.Handle` (ReleaseExpiredHoldsCommandHandler.cs:50-95), which deliberately forces no operation transition (see its class comment, 34-41) and calls `ReleaseAsync(tenantId, holdId, Expired)`; that flips the hold `Active → Released` and decrements `HeldCapacity` by N. Net result: the slot reports the seats fully free while a terminal `Booked` operation occupies them. It never self-heals — `CancelBookingCommandHandler`:262-269 resolves `GetBookedOperationForBookingAsync` and calls `ReleaseFinalizedByOperationAsync`, which only touches **Finalized** holds; `CompensateOperationCommandHandler`:134/250 releases only **Active** ones; `ResolveManualReviewCommandHandler`:383 releases only **Finalized** ones. A hold left Active and then swept to Released is invisible to all three.

*(b) Hold already lapsed when reconcile runs.* Reconcile books anyway with zero capacity accounting. This is not exotic: the `retry_budget_exhausted` and `finalize_auth_error` routes park an operation in `Reconciling` for as long as the driver takes to re-dispatch, and the hold TTL is 45 minutes. This is precisely the case `FinalizeBookingCommandHandler` refuses at :496-527, where `FinalizeAgainstOperationAsync` returning `HoldNoLongerValid` routes `Finalizing → CompensationRequired` (reason `hold_no_longer_valid`) plus an `operation.hold_no_longer_valid` audit event, and explicitly does not emit `booking_confirmed`.

**The primitive the fix would call.** `FirstPartyCapacityReservation.FinalizeAgainstOperationAsync(tenantId, operationId, workflowStep, ct)` (FirstPartyCapacityReservation.cs:196-254): no hold row → `NotTracked` (204-205); `Active` → conditional `ExecuteUpdateAsync` guarded on `Status == Active` (212-220), and on `rows == 1` moves the slot `held → booked` when `SlotId` is non-null (226-236) returning `Finalized`; on `rows == 0` re-reads and returns `Finalized` or `HoldNoLongerValid` (241-245); already `Finalized` → `Finalized` with no second slot move (249-250); `Expired`/`Released`/`Reconciling` → `HoldNoLongerValid` (252-253). The workflow step string a create op's hold is stored under is `"create"` (ReserveCapacityCommandHandler:146). `HoldStatus.Reconciling` is declared in the pg enum (HoldStatus.cs:26-27) but is never written anywhere in `apps/api/src`.

**The structural blocker for the proposed routing.** `Reconciling → CompensationRequired` is not a legal edge. `OperationStateMachine.AllowedTransitions` gives `[Reconciling] = { Held, Booked, AlternativesRequired, ManualReview }` (OperationStateMachine.cs:73-79); only `Finalizing` (67-72) has an edge to `CompensationRequired`. `BookingOperationRepository.TryTransitionStatusAsync` calls `OperationStateMachine.EnsureAllowed(expectedStatus, next)` on line 71 of every status write, so such a call throws `InvalidStateTransitionException` today; `AdvanceBookingOperationCommandHandler` catches it, persists a poison work item + `notification.still_confirming.v1` + audit and dead-letters the transport message (Inv-14), leaving the operation stuck in `Reconciling`. The edge set is verbatim from spec 06 §6.1 (docs/specs/06-booking-workflow-and-fulfillment.md:205-208), so the routing the issue proposes needs a spec amendment as well as a code change. The existing precedent for the alternative is `ResolveManualReviewCommandHandler`:274-291, which calls `FinalizeAgainstOperationAsync` best-effort on a create resolved as Booked and deliberately accepts `HoldNoLongerValid` as a discrepancy for the operator rather than refusing.

**Existing coverage of this path.** `ReconcileOperationCommandHandlerTests` (11 cases, 492 lines) builds the handler with ten mocks at lines 36-39 and never mentions capacity. `ReconciliationTests` (integration, 468 lines) drives the three headline scenarios (FM#2 at 156, FM#3 at 283, ambiguous-classification at 369) with operations that seed no `capacity_slots` and no `capacity_holds` rows at all — a grep of that file for `CapacitySlot`/`CapacityHold`/`CanonicalPayload` returns nothing. So no test in the repository exercises reconcile on a first-party-tracked operation, and the `FinalizeAgainstHoldTests` class doc at line 79 still describes the pre-PR-#54 behaviour ("op routed to Reconciling") that its own test at 372-455 now contradicts.

### The actual defect, as verified

The code observation at the heart of part 1 is CORRECT — `ReconcileOperationCommandHandler` transitions `Reconciling → Booked` with no capacity settlement — but the issue's reachability and severity framing is wrong in both directions, and part 2 is already implemented.

WHAT IS TRUE: the reconcile effect-proven branch confirms a booking with zero capacity work.
