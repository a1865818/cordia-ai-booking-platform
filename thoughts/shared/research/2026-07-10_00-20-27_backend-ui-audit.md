# Backend UI Audit

## Summary

- **12 feature-bearing controllers** (plus Ping/Health) exposing ~30 endpoints across bookings, booking operations, waitlist, menu publishing, preorder, catalog, verification/identity, consent, dead-letter replay, notification webhooks, and conversation-session consent.
- **LangGraph agent** streams a full voice/conversation pipeline (transcript partial/final, agent text deltas, tool progress, TTS audio, barge-in, turn-cancelled) — `apps/langgraph/cordia_agent/streaming_models.py`.
- **Frontend today**: 3 pages only — `HomePage`, `ConsolePage` (route `/dashboard`), `NotFoundPage` (`apps/web/src/router.tsx`). **Effectively every feature surface is missing.**
- Required: **~12 pages** across three personas (operator/staff, admin, end customer) plus a cross-cutting component kit. 0 exist, 1 partial (ConsolePage shell), rest missing.

## Backend feature inventory

### Bookings & Manage Booking (`BookingsController.cs`, spec 08)
- `GET /api/bookings?phone_e164|booking_reference|email` — minimized manageable-booking candidates (identity-first lookup).
- `GET /api/bookings/{id}` — verification-leveled projection; `403 RequiresVerification` when grant (`X-Grant-Id`) is missing/insufficient.
- `POST /api/bookings/{id}/changes:validate` — dry-run change validation.
- `POST /api/bookings/{id}/modifications`, `POST .../cancellations`, `POST /api/bookings` (create).
- Lifecycle enum: `Confirmed, ModificationPending, CancellationPending, Cancelled` (`Enums/BookingLifecycleStatus.cs`).

### Booking operations saga (`BookingOperationsController.cs`, specs 06–07)
- `GET /{operationId}` status; `POST .../cancel`, `.../resume`, `.../resolve` (operator resolution), `.../alternatives`.
- `OperationStatus`: `Accepted, Validating, AwaitingUserAction, ReservingCapacity, Held, AwaitingPayment, Finalizing, Booked, AlternativesRequired, Reconciling, CompensationRequired, ManualReview, Rejected, Expired, Waitlisted, FailedFinal` — a rich state machine that drives status badges and which action buttons are legal per state.

### Verification / identity (`VerificationsController.cs`, spec 08)
- `POST /api/verifications` (start), `GET /{id}` (status), `POST /{id}/verify` (submit code). `VerificationLevel` gates booking detail depth.

### Waitlist (`WaitlistController.cs`, spec 11)
- `POST /enrollments`, `DELETE /enrollments/{id}`, `POST /offers/{id}/accept|decline`. `WaitlistOfferStatus` enum.

### Menu publishing workflow (`MenuController.cs`, spec 11)
- `POST /catalogs` (ingest) → `/review` → `/edit` → `/approve` → `/publish`; `CatalogStatus` + `ArtifactScanResult` (uploaded artifact scanning). A classic staged-approval workflow UI.

### Catalog & preorder (`CatalogController.cs`, `PreorderController.cs`, spec 11)
- `GET /api/catalog/items`, `GET /items/{id}`; preorder saga `POST /sagas/{id}/convert-standalone`, `POST /sagas/{id}/cancel`; `PreorderSagaState`, `ItemReservationStatus`.

### Consent & privacy (`ConsentPoliciesController.cs`, `ConversationSessionsController.cs`, spec 14)
- `GET /api/consent-policies`; `POST /api/conversation-sessions/{id}/consent`. `ConsentState`, `ConsentDecision`. Spec 14 also added audit writer, reason-coded operator actions, log scrubbing, retention sweeps (recent commits) — implies audit-trail viewing needs.

### Ops / reliability (`DeadLetterMessagesController.cs`, `NotificationWebhooksController.cs`, specs 05, 10)
- `POST /api/dead-letter-messages/replay` (reason-coded operator action, `DlqReplayState`); delivery-receipt webhook ingestion; `NotificationState`, `EndpointStatus`, `ScheduledJobStatus`, outbox/inbox enums back an ops dashboard.

### LangGraph agent (`apps/langgraph/cordia_agent/`, specs 01–03)
- Streaming frames: `TranscriptPartialFrame/FinalFrame`, `AgentTextDeltaFrame/FinalFrame`, `ToolProgressFrame`, `TtsAudioDeltaFrame`, `AudioStartedFrame`, `BargeInFrame`, `TurnCancelledFrame` wrapped in `StreamFrameEnvelope`.
- Modules for slots, readback confirmation, revisions, safety, recovery — the conversation UI must render tool calls, confirmations/readbacks, and interruptions.

## Cross-cutting components

- **Tenant context**: every API call needs `X-Tenant-Id` (`BookingsController.cs:33`) — tenant switcher in the console header + API client middleware.
- **Status badge system** keyed to the domain enums above (single component, enum-driven colors), sourced from generated TS types in `libs/shared-schemas/generated/typescript`.
- **Reason-code dialog** — reusable confirm dialog with mandatory reason selection for operator actions (resolve, replay, cancel), matching the spec-14 audit spine.
- **Version-token / 409 conflict handling** — toast + "reload and retry" pattern (see `cordia-dotnet-conventions` memory: version tokens on mutations).
- **Verification gate** — wrapper that catches 403 `RequiresVerification` and mounts the OTP flow.
- **Idempotency-key handling** in the typed fetch client for POST mutations (spec 04).
- Standard loading / empty / error states; ProblemDetails-aware error renderer.

## Suggested build order

1. **Cross-cutting kit first**: typed API client (tenant header, idempotency key, 409 handling), status-badge system, reason-code dialog.
2. **Operator bookings list + detail** (highest daily value, simplest reads).
3. **Operations board** (unlocks ManualReview/CompensationRequired handling — the reliability payoff).
4. **Customer manage-booking + verification flow** (self-service deflection).
5. **Waitlist board + offer landing page**.
6. **Menu publishing wizard**, then **preorder sagas**.
7. **Admin DLQ + notifications monitor**.
8. **Conversation session viewer / voice widget** (largest lift; depends on streaming plumbing).
