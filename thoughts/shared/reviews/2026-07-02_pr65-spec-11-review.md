- **Date:** 2026-07-02
- **PR:** #65 (`feat/spec-11` → `main`, head `1a0145c`)
- **Spec:** [`docs/specs/11-waitlist-menu-preorder.md`](../../../docs/specs/11-waitlist-menu-preorder.md)
- **Scope:** full PR diff (~35.5k additions / 239 files; generated EF migration
  Designer files, model snapshot, OpenAPI JSON, and `PydanticSharedDefs.json`
  excluded from hand review)
- **Method:** `/review` medium effort — 8 finder angles (3 correctness, 3
  cleanup, altitude, conventions) → dedup → per-candidate verification against
  the checkout. Three finder angles (removed-behavior, cross-file tracer,
  reuse) were lost to a session rate limit; verification for all surviving

## Overview

The PR implements all three spec-11 verticals in `apps/api` (plus LangGraph
contracts): waitlist enroll → match → offer → accept/expire with auto-book
grants, the menu upload → scan → extract → review → approve → publish
pipeline, and a pre-order saga that revalidates items, reserves them, and
delegates the booking to the spec-06 engine.

The menu-ingestion vertical is solid — published-only reads, state-machine
guards, and isolation boundaries all check out. The problems concentrate in
the waitlist/pre-order messaging seams: several outbox events are emitted
with **no registered consumer**, and the transport silently marks unregistered
types as delivered, so entire customer-facing flows are dead without any
error surfacing.

## Findings (most severe first)

### 1. Waitlist offer notifications are silently dropped — the §5.1 happy path is unreachable

**File:** `apps/api/src/Cordia.Application/Handlers/Waitlist/Match/MatchWaitlistOfferCommandHandler.cs:139`

The handler emits `waitlist.offer.notified.v1` to the outbox, but the
`ConsumerRegistry` in `ApplicationServiceCollectionExtensions.cs` registers no
consumer for it. The spec-10 comment there (line 159 — *"Spec 11 will register
its own Critical WaitlistOffer message type"*) was never fulfilled, and
`NotificationEvent.WaitlistOffer` is defined but unused. The `waitlist.`
prefix routes the message to the waitlist lane, where `PostgresMessageTransport`
treats an unregistered type as *delivered* (the outbox row is marked published).

**Failure scenario:** slot frees → hold reserved → offer created → **customer
is never told** → offer expires at `held_until` → re-match to the next
enrollee, who also never hears. Every non-auto-book offer in the system
silently expires unanswered. `waitlist.offer.expired.v1`
(`ExpireWaitlistOfferCommandHandler.cs:32`) is dropped the same way.

### 2. Failed pre-order revalidation produces zero customer-visible outcome and a permanently stuck operation

**File:** `apps/api/src/Cordia.Application/Handlers/Preorder/StartSaga/StartPreorderSagaCommandHandler.cs:116`

On stale items the saga advances `Revalidating → FailedFinal` and emits only
`preorder.alternatives_required.v1` — which, like finding 1, has no registered
consumer and is silently dropped. Because pre-order operations skip the
`booking.command.requested.v1` emit in `SubmitConfirmedIntentCommandHandler`
(line 250), the 06 engine never starts either, and nothing ever transitions
the `booking_operations` row out of `Accepted`.

**Failure scenario:** customer confirms a pre-order; the restaurant
republishes the menu with a new price before the saga starts → the confirmed
intent dies with no re-confirmation prompt (Inv-10) and no failure
notification (Inv-14).

### 3. A successfully accepted enrollee stays eligible and can be offered (or silently auto-booked) a second table

**File:** `apps/api/src/Cordia.Application/Handlers/Waitlist/Accept/AcceptWaitlistOfferCommandHandler.cs:122`

The claim-won branch only writes an audit event; only the *lost-claim*
reconcile path marks the enrollment fulfilled (*"so the enrollee is never
re-offered → no double-book"* — the PR's own stated invariant).
`WaitlistEnrollmentRepository.FindEligibleAsync` (lines 46–57) excludes only
live offers (`Pending`/`Matched`/`Offered`) and same-slot offers, so an
`Accepted` offer for slot A excludes nothing when slot B frees inside the same
acceptance window.

**Failure scenario:** enrollee accepts an offer for slot A (booking minted); a
second opening B within their `[AcceptableFrom, AcceptableTo]` window frees →
match finds them eligible again → new offer; with an `AutoBookGrant`, the
platform books them a second table with no customer action.

### 4. A pre-order that fails on capacity leaves the operation parked live in `AlternativesRequired`, allowing a contradictory second outcome

**File:** `apps/api/src/Cordia.Application/Handlers/BookingFulfillment/ReserveCapacity/ReserveCapacityCommandHandler.cs:154`

The pre-order branch swaps only the outgoing message (saga `booking_failed`
instead of the alternatives notification) but still transitions the operation
`ReservingCapacity → AlternativesRequired` — a non-terminal,
customer-responsive state. `RespondToAlternativesCommandHandler` guards its
Decline branch with `FailedOutcomeType(current.IsPreorder)` but its Waitlist
branch (line 59) is unguarded.

**Failure scenario:** after the saga has compensated items and emitted the one
combined failure outcome, a late "waitlist me" response still moves the op to
`Waitlisted` and emits customer-facing `notification.waitlisted.v1` — a
second, contradictory outcome (Inv-8 violation).

### 5. `ManualReview` is unreachable — the §21.4 operator+customer resolution surface is dead code

**File:** `apps/api/src/Cordia.Domain/Preorder/PreorderSagaStateMachine.cs:95`

The only writers into `ManualReview` come from `Reconciling`
(`ReconcilePreorderSagaCommandHandler.cs:172`) and `CompensatingBooking`
(`CompensatePreorderBookingCommandHandler.cs:52`), and no code anywhere
transitions a saga *into* either state (`CommitPreorderCommandHandler` can
only complete or settle; step timeouts enqueue reconcile *messages* without
changing state).

**Consequences:**

- The `CancelPreorderManualReview` / `ConvertPreorderToStandalone` endpoints,
  the whole `CompensateBooking` message chain (handler + registration +
  tests, ~250 lines), and the `Reconciling` edge block (~11 phantom edges)
  can never execute.
- The spec's *"booking ok but pre-order not → ManualReview"* park is
  effectively unimplemented.
- Latent within this: `CancelPreorderManualReviewCommandHandler` never
  releases the saga's item reservation (`IPreorderItemReservation` isn't even
  injected), so the moment `ManualReview` gets wired, cancelling one leaks
  reserved items — violating §5.3's "FailedFinal: holds/items released".

### 6. Catalog search interpolates the raw user query into an ILIKE pattern without escaping `%` / `_` / `\`

**File:** `apps/api/src/Cordia.Infrastructure/Repositories/VendorCatalogRepository.cs:32`

**Failure scenario:** `GET /api/catalog/items?query=\` yields the pattern
`%\%`, which PostgreSQL rejects with error 22025 (*"LIKE pattern must not end
with escape character"*) → unhandled `PostgresException` → HTTP 500 on a
customer-facing foreground read path. `query=100%` or `query=_` match
everything/any character instead of literals, so the foreground agent's
"narrow keyword search" returns arbitrary items.

### 7. Cancelled-enrollment guard runs before the Accepted-replay branch, breaking the documented idempotent replay with a 409

**File:** `apps/api/src/Cordia.Application/Handlers/Waitlist/Accept/AcceptWaitlistOfferCommandHandler.cs:75`

The class doc promises *"re-accepting an accepted offer is a no-op,"* and the
replay branch at line 88 exists for exactly that. But the `CancelledAt` check
at line 75 precedes it — and `ReconcileWaitlistAcceptCommandHandler` marks
*fulfillment* by stamping `CancelledAt` via `CancelAsync`.

**Failure scenario:** a legitimate accept retry (duplicate delivery, user
retry after a crash) on an offer whose enrollment was since cancelled or
reconcile-fulfilled throws `InvalidWaitlistOfferTransitionException` → HTTP
409 for a booking that already exists.

### 8. Enrollment verification level is an unvalidated free-form string, silently coerced to `Unverified` at accept time

**File:** `apps/api/src/Cordia.Domain/Entities/WaitlistEnrollment.cs:52`

`EnrollWaitlistValidator` has no rule for it, `WaitlistAcceptSubmission.Build`
copies it verbatim into the minted confirmation (line 91), and
`ConfirmationMappings.MapVerificationLevel` maps any unrecognized value (e.g.
`"verified"`, `"identityVerified"` instead of `"identity_verified"`) to
`Unverified` with no error anywhere.

**Failure scenario:** the captured assurance level — the point of binding the
booking to the enrolled customer's identity (§5.1 "verified follow-up") — is
silently discarded. The domain `VerificationLevel` enum already exists; parse
at the enrollment edge instead.

## Cut by the 8-finding cap (real, lower priority)

- **Revalidation N+1:** `LiveItemRevalidationService` issues one sequential DB
  query per pre-order line inside the inbox transaction — batch with
  `WHERE item_id IN (...)` (spec §7 budget: p95 < 150 ms).
- **Unbounded eligibility load:** `FindEligibleAsync` loads every eligible
  enrollee to use only `[0]` — use `FirstOrDefaultAsync` (and an index on
  `(tenant_id, location_id, service_id, created_at)`).
- **Sweeper scan:** the recovery sweeper full-scans `preorder_sagas` every
  30 s with no supporting index and materializes full entities to read three
  ID columns.
- **Duplicated accept protocol:** `AcceptWaitlistOffer` and
  `AutoAcceptWaitlistOffer` duplicate the same ~100-line mint-then-claim
  protocol; a fix applied to one will silently miss the other.
- **Missing validators:** `AcceptWaitlistOfferCommand`,
  `DeclineWaitlistOfferCommand`, `ConvertPreorderToStandaloneCommand`, and
  `CancelPreorderManualReviewCommand` are dispatched from controllers with no
  `AbstractValidator`, though `docs/dotnet-api-patterns.md` designates
  validators as the sole source of required-field enforcement.

## Root-cause note

Findings 1 and 2 share one root cause worth fixing at the mechanism level
rather than per-message: **outbox events whose type has no registered consumer
are marked delivered and vanish** (`PostgresMessageTransport` treats an empty
registry match as success). Making unregistered-but-routable types loud —
e.g. dead-lettering them the way `OutboxPublisherHostedService` already
dead-letters *unroutable* types — would have caught both findings and will
catch the next one.
